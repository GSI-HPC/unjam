## The format decision

A recorder runs **inside the job**. Slurm can SIGKILL it after `KillWait`, the node can run out of memory, and the node can crash. So the on-disk format must stay readable up to the last complete write, and the recorder must use little memory.

| Option | Verdict |
|---|---|
| **Arrow IPC stream** (`.arrows`), LZ4_FRAME | **Chosen.** Every complete batch is readable after a kill. pyarrow, polars and others read it. One replay path |
| Parquet, written in the job | Parquet writes its footer only on close. A recorder killed after `KillWait` leaves an unreadable file |
| `unjam convert` to Parquet | Cut (D35): about +3 MB of binary, about 30 crates and 110 lines. A pyarrow one-liner does the same, and CI tests it |
| zstd | A C library through `zstd-sys`: FFI `unsafe`, and it breaks clean static musl builds. LZ4 is pure Rust (`lz4_flex`, forced to its safe codec) |

## Batches and keyframes

1. **Create** the file new with mode 0600 (`create_new`; it holds command lines), wrap it in a `BufWriter` and write the schema message at once.
2. **Collect** rows in arrow-array builders. Cut a batch every **10 s or 8,192 rows**, whichever comes first; write and flush it.
3. **Keyframe rule.** The first row of each entity in a batch carries `path`, `comm`, `cmdline`, `ppid` and `start`. Every batch therefore decodes on its own.
4. **End** (normal exit or SIGTERM): write the last batch, then the end-of-stream marker.
5. **Crash** (SIGKILL, OOM, node crash): at most the open batch (10 s) is lost.
6. **No `fsync`** on the hot path. It is expensive on Lustre and GPFS, and the page cache survives a process kill.

**Memory.** At the 8,192-row cap: 8,192 rows × about 30 columns × 8 bytes ≈ 2 MB, plus validity bitmaps and strings: at most about 3 MB. Typically about 100 KB. 65,536-row batches would need about 16 MB in the job (D16).

## The schema comes from the descriptors

`record::schema(&Columns, meta)` makes one `UInt64` column per metric, named by the metric, with `unjam.unit`, `unjam.kind` and `unjam.source` as field metadata (D17). A new source therefore adds columns with **no change in `record.rs`**. A wide table was chosen over a narrow entity-attribute-value table, which would repeat a string name per value and compress worse. The columns are in [Recording format](/unjam/reference/recording-format/).

## Two writers, one format

- **`unjam record`**: the sampler feeds a local `State`; `Writer` writes each tick from it as a **complete snapshot** of the step's tasks on this node. `unjam.source=record`.
- **The viewer** (<kbd>r</kbd>, `--record DIR`): `Rec` feeds what the viewer receives into one `Writer` per node (`unjam.source=tui`). A node's tick is written when its **next** tick starts, because an agent sends a tick's structure before its `T`; writing at `T` would mix in the next tick's structure. A node silent for three intervals before the recording starts is not recorded.

## Replay and seeking

- **Open.** Wrap the file in `Counting`, a `Read` that counts bytes. Decode only the `ts` column of each batch (`StreamReader` with a projection) and build an index of `(byte offset, first ts)`. Keep the schema message bytes.
- **Seek(t).** Binary-search the index. Decode one batch with `Cursor::new(schema_bytes).chain(file_at(offset))`. Going back, rebuild from the batch that holds **t − 120 s** (twice the longest interval), so each entity has its previous sample and rates match forward play.
- **Several files** share one cursor over **sampling rounds**: ticks of different nodes that are closer than half the shortest tick gap form one round. One step moves every node by one tick.
- **Memory.** One decoded batch per file: about 250 KB per node typically.
- Validation stays on: `with_skip_validation` (an `unsafe fn`) is never called.
- **Truncated files** replay up to the last complete batch, with one warning: "truncated at byte N". A unit test truncates a journal at 200 random offsets; each must give its valid prefix and never panic.

:::caution[Replay inputs must be trusted]
arrow-ipc 60 allocates an LZ4 buffer at the uncompressed length the file states, before any check. A crafted file can therefore abort replay with an allocation failure. The fix belongs upstream (a capped preallocation).
:::

## Interop

Tested in integration test IT 6: `pa.ipc.open_stream` reads `.arrows` with field metadata, and the pyarrow recipe writes a Parquet file that `pq.read_table` reads back with the same row count. Other readers are expected to work but are not claimed.
